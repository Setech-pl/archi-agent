# Archi Agent gauntlet

Use only on an explicit `$archi-agent-gauntlet` request. Identify the requested mode: implement and prepare for owner smoke, resume after failed smoke, or finalize after owner smoke PASS. An explicit invocation alone grants no implementation or Git publication permission. Follow the current `AGENTS.md` and approved milestone scope.

1. **Preflight.** Resolve the repository root; read every applicable `AGENTS.md`. Record branch, HEAD/base commit, upstream, tracking and remote refs, working tree, staging, and Node/npm versions. Require a clean start unless the owner explicitly authorizes otherwise. Stop on mismatched branch, refs, or other preconditions. Never switch branches, stash, reset, discard, overwrite, merge, rebase, amend, or force push without explicit authorization.
2. **Scope.** Read the current project state, roadmap, milestone specification, architecture and extension documentation. Extract acceptance criteria, exclusions, deferred work, affected surfaces, gates and owner smoke steps. Separate verified facts from assumptions. Ask before deciding an absent architecture, security, compatibility, persistence or public behavior contract. Do not expand scope silently. Read [project profile](references/project-profile.md) for stable project constraints; current repository documents decide milestone order and status.
3. **Implement.** Require the repository's approved implementation prompt or equivalent explicit authorization. Implement only that milestone, including necessary tests and documentation. Preserve public commands, compatibility, self-contained packaging, local-first and fail-closed behavior unless the approved scope changes them. Avoid speculative dependencies and layers. Do not commit or push during implementation.
4. **Verify and review.** Run focused deterministic tests, affected typechecks/build checks and whitespace checks on tracked, staged and untracked files first; fix failures without weakening checks. Then commission an independent, read-only reviewer under [reviewer protocol](references/reviewer-protocol.md). Fix valid high/medium findings, rerun affected checks and re-review, at most three rounds. High/medium findings after round three block readiness.
5. **Full gates and artifact.** After review passes, run the current repository gates sequentially. Inspect `package.json` and `vscode-extension/package.json` before using [the gate runner](scripts/run-gates.sh); use `--dry-run` to inspect its planned commands and `--with-install` when `npm ci` is needed. Use `--vsix-out /absolute/directory` to package and verify a unique candidate without replacing earlier VSIX. Use `--audit-unavailable` only after confirming the network is unavailable, and report that audit was not run. Record exact results and justified narrow exceptions. For UX3, run `npm run ux3:gauntlet`, which extends this runner with packaged-runtime, real Extension Host settings and real UI checks; required NOT_RUN or FAIL blocks readiness. Controlled editor answers are source/host evidence, never real UI evidence, and automated smoke is never owner smoke. For affected VSIX/runtime/worker surfaces, inspect the final package and run relevant smoke from extracted artifacts outside the repo dependency tree when needed; check privacy, source immutability, cancellation and partial-result behavior, VSIX size and SHA-256. Skip irrelevant artifact work for documentation-only changes.
6. **Owner boundary.** Follow the owner decision recorded in `docs/development-workflow.md`: milestone loops use implementation, gauntlet, independent review and an explicitly authorized local checkpoint. Record `OWNER_SMOKE: DEFERRED` until the owner reports a result; deferred smoke does not block the next authorized milestone. Required FAIL/NOT_RUN and open high/medium findings still block checkpoints. Never claim manual UI testing from automated evidence.
7. **Finalization.** After required gates and independent review pass, update status, inspect the exact staging scope and make only the explicitly authorized local commit. Push, main integration, tags and publication require separate authorization; local checkpoint permission does not grant them. For separately requested release finalization, read [finalization protocol](references/finalization-protocol.md) and apply the owner's current smoke policy. Use the [report template](references/report-template.md) to distinguish command evidence, reviewer conclusions, owner reports, warnings and deferred work.
