# Offline Space Mission demo

The offline demo runs the complete ArchGround pipeline on the synthetic Space Mission sample and
writes a validated PlantUML sequence diagram together with its grounding report. It needs no
language model, no network connection and no editor.

## Prerequisites

- Node.js 22.12 or later.
- Dependencies already installed in `node_modules` (TypeScript and Zod). The demo adds no
  dependency and installs nothing.
- Run the commands from the project root.

## Commands

    npm run demo:dry-run
    npm run demo

`npm run demo:dry-run` builds the demo and runs every stage, including output planning, then
prints a short summary and the planned paths. It creates no directory and no file.

`npm run demo` builds the demo, runs every stage and writes the artifact pair. It prints the
project-relative paths of the two files.

Both commands start with `npm run build:demo`, which compiles the demo with the existing
TypeScript compiler into the ignored `dist` directory. `scripts/prepare-demo-output.mjs` removes
only that `dist` directory before compiling and afterwards writes `dist/package.json`, which marks
the compiled output as an ES module. The script accepts no path argument and refuses to act when
`dist` is a link or not a directory.

The console output contains the generator type, participant and message counts (synchronous,
asynchronous and response messages, plus a separate count of self-messages, which overlaps those
three), the number of warnings, the grounding digest and the artifact paths. It never contains the flow text, the pack
tables or the report.

## Output

The first run writes:

    architecture-diagrams/space-mission/sequence/telemetry-command-flow.puml
    architecture-diagrams/space-mission/sequence/telemetry-command-flow.grounding.json

The `architecture-diagrams` directory is ignored by Git.

### Paired versioning

The diagram and its report always share one file-name base. An existing file is never
overwritten: the next run writes

    telemetry-command-flow-v2.puml
    telemetry-command-flow-v2.grounding.json

and later runs continue with `-v3`, `-v4` and so on. The version is one more than the highest
version present for either extension, compared without letter case, so a single leftover file
still moves both files to the next version. The search stops at version 999.

### Safe writing

- Paths are relative to the selected output root and must stay inside it; parent segments,
  absolute paths, drive letters, backslashes and reserved device names are rejected.
- Links and junctions anywhere on the way are rejected instead of followed.
- Both destinations are checked before anything is written.
- Both contents are first written to exclusive temporary files in the target directory.
- Only after both temporary writes succeed does each file receive its final name. The final name
  is created as a hard link (or an exclusive copy where hard links are unsupported), so an entry
  that appeared in the meantime is never replaced.
- On failure, only files created by the current attempt are removed. A directory created for the
  output is left in place, empty.

### Golden outputs

`samples/space-mission/expected/` holds the first-version pair produced by the pipeline itself.
A test compares the in-memory demo output with these files byte for byte. They were generated by
running the pipeline, not written by hand.

## Pipeline

1. Read the flow document `samples/space-mission/flows/telemetry-command-flow.md` (bounded,
   UTF-8 only, no NUL bytes, no links, inside the project).
2. Load the five Knowledge Pack files from `samples/space-mission/architecture`.
3. Build the minimal grounded context; stop when grounding is blocked.
4. Call the injected sequence-model generator with the parsed flow, the minimal context and its
   digest.
5. Validate the untrusted result against the strict generated-model schema.
6. Normalize it deterministically.
7. Validate structure, fragments, text safety and participant grounding.
8. Validate relationships, directions and interaction modes.
9. Apply the interface-name policy.
10. Render PlantUML from the cleaned model only.
11. Validate the emitted PlantUML subset structurally.
12. Build the grounding report.
13. Return both artifacts in memory.
14. Only then plan and write the artifact pair.

Normal validation failures are values, not exceptions. The outcomes are `success`,
`grounding-blocked`, `invalid-generator-output`, `semantic-validation-failed`,
`render-validation-failed` and `output-failed`.

## The grounding report

The report is UTF-8 JSON with two-space indentation, a fixed key order, sorted arrays and a final
newline. It records the schema version, diagram name, flow name, author, language, grounding
digest, generator type, the project-relative flow and pack locations, every grounded participant
with identifier, kinds, canonical name, pack source line and flow mention positions, confirmed new
participants, the relationships and rules of the minimal context with the messages they support,
ambiguity selections, message verification, fragment ranges, warnings, a validation summary and the
two paired file names.

It does not contain the flow text, pack file contents, message labels, prompts, raw generator
output, timestamps, absolute paths, environment values, credentials or user names.

## The scripted generator

The demo uses `ScriptedSpaceMissionGenerator`, generator type `scripted-demo`. It is a fixed,
deterministic script for this synthetic flow and is not a language model. It takes every
participant from the grounded context, refers to it by Knowledge Pack element identifier, uses only
relationships, modes and interface names of the context, and stops with an error instead of
inventing anything when the expected context is missing. Its output still passes through every
validation stage.

## What the demo proves

- The local pipeline from flow and pack to diagram and report works end to end.
- Only grounded participants, relationships and modes reach the diagram.
- PlantUML is built from validated structured data only and passes the local subset check.
- The result is deterministic: the same inputs give the same bytes.
- Output is written safely and paired, and a second run does not overwrite the first.

## What the demo does not prove

- No language model is called, so the quality of model-generated diagrams is not shown.
- The official PlantUML engine is not executed. The local validator checks only the exact subset
  that the renderer emits; it is a structural check, not a rendering test.
- There is no editor integration and no packaged extension.

## Owner decisions applied

1. A rule enters the grounded context only when both endpoints are selected for the diagram.
2. The author is part of the context and the artifact metadata but not of the grounding digest.
3. Ordinary matching does not treat hyphens and underscores as spaces.
4. Looser hyphen and underscore comparison is used only to stop a `[NEW: Name]` participant from
   impersonating a known element.
5. Known generated participants are referenced by Knowledge Pack element identifier.
6. An interface name that the applicable grounded relationship does not declare is removed with a
   warning; no replacement is guessed.
7. An ungrounded participant, endpoint, relationship or interaction mode is a blocking error.
8. This phase uses the deterministic scripted generator only, and it is never described as a
   language model.

INTERNAL is an interface classification, not a self-message marker. Between two different
participants it is valid only as an explicit grounded INTERNAL relationship with the same direction
and mode; the demo draws the Flight Controller submitting the command to Mission Control through
its declared synchronous INTERNAL console relationship. A self-message is decided only by equal
sender and receiver; it uses INTERNAL, needs no relationship and never authorizes an interaction
between different participants.

## Next phase

Phase 3G is planned to add real generator adapters behind the same provider-neutral port: hosted
model APIs (OpenAI, Anthropic, OpenRouter), an editor-provided model (Copilot) and local
OpenAI-compatible endpoints such as LM Studio. None of them exists yet. Every adapter will receive
only the minimal grounded context and its output will pass the same validation pipeline.
